# 3. Projects

## 3.1 Layout

A WaSL project is a directory:

```
calc/
├── wasl.toml          # manifest: identity of the package
├── src/               # source files
│   ├── calc.wasl
│   └── util/
│       └── clamp.wasl
├── tests/             # tests, run by `weasel test` (§ 3.6)
│   └── calc_test.wasl
└── build/             # generated by `weasel build`
    └── calculator.wasm
```

- The **root** of the project is the directory that contains `wasl.toml` and `src/`.
- The tools operate on the project whose root is the **current directory** (§ 14.1). They do not search parent directories.

## 3.2 Manifest `wasl.toml`

The manifest is a [TOML](https://toml.io) file that declares the identity of the package and its dependencies.

```toml
[package]
namespace = "example"
name = "calc"
version = "0.1.0"
```

| Field | Required | Rule |
|---|---|---|
| `namespace` | yes | lowercase WIT identifier: words of ASCII lowercase letters and digits, separated by `-`, each word starting with a letter (e.g. `example`, `my-org`) |
| `name` | yes | same rule as `namespace` (e.g. `calc`, `todo-api`) |
| `version` | yes | SemVer version `MAJOR.MINOR.PATCH`, three decimal numbers without leading zeros (`0.1.0`, `1.12.3`), optionally followed by a pre-release (`-alpha.1`) or build (`+build.5`) suffix |

- The file contains the table `[package]`, with exactly these three fields, and optionally the table `[dependencies]` (§ 3.5). Any other table or field is an error.
- The identity of the WIT package is `namespace:name@version`, e.g. `example:calc@0.1.0`.
- An invalid manifest is reported with code E0200 (§ 11.4), including an invalid `[dependencies]` table.

## 3.3 Source files

- Every file whose name ends with `.wasl` in `src/` or in any sub-directory of `src/` is a source file of the package. Other files are ignored.
- Source files are UTF-8 (§ 4.1).
- All the source files form **one package**: a declaration of any file is visible in every file.
- File and directory names have **no meaning** for the language. By convention, a file is named after the main interface or world it declares.
- The order of the declarations does not matter: a declaration can be used before it is declared, including from another file.
- Files are processed in a fixed order: sorted by the byte order of their path, written relative to the root with `/` separators (e.g. `src/a.wasl`, then `src/b.wasl`, then `src/b/c.wasl`). This order only decides which error is reported first (§ 11.2).
- In diagnostics, a file is designated by this relative path, e.g. `src/util/clamp.wasl`.

## 3.4 Outputs

- `weasel build <world>` writes the component of the world `<world>` to `build/<world>.wasm`, where `<world>` is the WaSL name of the world (`build/calculator.wasm`). `weasel build --all` builds every world.
- Each world is built separately (§ 2.3): a project with three worlds produces three files, with three builds.
- A world that includes `wasl:std/service` or `wasl:std/command` (§ 17.1) is built like the others, in one component: the file is a WASI 0.3 HTTP service or command, ready for wasmtime.
- `build/` only contains generated files; `weasel clean` removes it.
- A component is a standard WebAssembly component: it can be inspected with `wasm-tools`, run with wasmtime and composed with other components.

## 3.5 Dependencies

A project depends on another package when one of its worlds imports or exports an interface of that package (§ 2.4.2, § 2.5). Dependencies are declared in the `[dependencies]` table of the manifest:

```toml
[package]
namespace = "example"
name = "checkout"
version = "0.1.0"

[dependencies]
"example:catalog" = { path = "../catalog" }   # another WaSL project, or a directory of WIT files
"wasi:cli" = "0.2.6"                          # a WIT package from a registry
"wasi:io" = "0.2.6"
```

| Key | Value | Meaning |
|---|---|---|
| `"namespace:name"` | `"MAJOR.MINOR.PATCH"` | the package at this exact version, fetched from a registry |
| `"namespace:name"` | `{ path = "<dir>" }` | the package found in `<dir>`, relative to the root of the project |

- The key is the WIT name of the package, quoted because it contains `:`. Its namespace and name follow § 3.2.
- A **version** is an exact SemVer version (§ 3.2), written in the generated WIT (§ 13.1). There are no version ranges: one dependency has one version, and the source code does not repeat it (§ 2.5).
- A **path** designates either a WaSL project, a directory that contains `wasl.toml`, whose package must have the name of the key and whose version is the one of its manifest; or a directory of `.wit` files, parsed as a WIT package with its `deps/` subdirectory, as `wit-parser` does, which must declare the package of the key.
- Every package that the source code names (`import example:catalog/carts;`) must be declared (E0215). Packages that a dependency uses without the source naming them, such as `wasi:io` for the types of `wasi:cli`, are resolved with it and need not be declared; the source can only name the packages declared in the manifest.
- A package cannot depend on itself, and two dependencies that resolve to two versions of the same package are an error (E0200).

**Registries.** A version is fetched with the crates of `wasm-pkg-tools` (`wkg`), from the registry that their configuration assigns to the namespace: `wasi` packages from `ghcr.io/webassembly` by default, and any OCI registry otherwise (§ 14.2). Fetched packages are cached by `wkg`, and the exact versions and digests are recorded in **`wkg.lock`**, at the root of the project, next to `wasl.toml`, in the format of `wkg`. The lock file is meant to be committed: a later build resolves each package to the version and digest it records. The configuration of `wkg` is its usual file, `~/.config/wasm-pkg/config.toml`, which also says how to reach private registries.

**Path dependencies on WaSL projects.** Only the WIT of the dependency is used to compile the project: its interfaces, types and functions, never its source code. The dependency is analyzed like a project of its own (chapter 11), and an error in it stops the build. Its components are built when they are needed to run the project (§ 14.2).

**The standard library.** *Specified, not available yet.* `wasl:std` (chapter 17) is the one **library** of 0.5: a dependency whose source code is compiled with the package. It is shipped inside `weasel`, at the version of the compiler, and every project depends on it without declaring it; `"wasl:std"` in `[dependencies]` is E0200. Its interfaces behave like interfaces of the package that no world imports:

- a file names them with `use wasl:std/<interface>;` (§ 6.6);
- the code of the functions that a world reaches is compiled into its component, as for the interfaces of the package (§ 2.3), and only that code;
- the interfaces of WASI that this code calls are imported by the component without being written in the world, at the version that the standard library uses: they are part of the library, as a call to `libc` is part of a C program. `weasel wit` shows them (§ 14.2). The packages of WASI that the standard library needs are resolved with it and need no entry in `[dependencies]`;
- a world can include `wasl:std/service` or `wasl:std/command`, the worlds of the library, and write the functions without body that they call (§ 2.4.3); the interfaces of the library are never exported (E0218);
- its errors are bugs of the library: the package is analyzed with the library as if it were part of it, and an error located in the library is reported with the path `wasl:std/<file>`.

Libraries other than `wasl:std`, written by users, come later ([ROADMAP.md](../../ROADMAP.md)): they will follow the same rules, declared in `[dependencies]`: nothing in the language is reserved to `wasl:std`.

## 3.6 Tests

*Specified, not available yet.*

The files of `tests/`, and of its sub-directories, whose name ends with `.wasl`, are **test files**. They follow the rules of § 3.3, and are analyzed with the package only by `weasel test` (§ 14.2): `weasel build` and `weasel check` ignore them.

```wasl
// tests/shop_test.wasl
use wasl:std/json;

interface shop_test {
  func total_of_two_lines() -> result<_, string> {
    local lines = [
      shop::order_line { sku: "pen", quantity: 3, unit_price: 150 },
      shop::order_line { sku: "ink", quantity: 1, unit_price: 900 },
    ];
    if (shop::total(lines) != 1350)
      return result.err("expected 1350, got " + u64.to_string(shop::total(lines)));
    return result.ok;
  }

  func parses_an_empty_order() -> result<_, string> {
    local order = shop::order_from_json(json::parse("{\"lines\": []}")?)?;
    if (list.len(order.lines) != 0)
      return result.err("expected no line");
    return result.ok;
  }
}
```

- A test file declares interfaces, like a source file; it cannot declare worlds or globals (E0226). Its interfaces can call every interface of the package, and the package cannot call them.
- A **test** is a function of an interface of a test file that has no parameter and returns `result<_, string>`, async or not. `ok` passes; `err(message)` fails with the message; a trap fails with the trap. The other functions of the test interfaces are helpers.
- Each test runs in a **new instance**: the globals start from their initial value, and a test cannot see what another one did.
- The name of a test is its path: `shop_test::total_of_two_lines`.
- A test that calls a function of an interface of another package, through an imported interface, needs that interface at run time: in 0.5, only the interfaces of WASI that `weasel` provides (§ 14.6) can be called from a test.
