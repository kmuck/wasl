# 16. Open questions

These questions were met while writing the target programs and the specification. Each one has a default in the chapters above; this list says where the default is weakest. Features already planned, such as async and the standard library, are in [ROADMAP.md](../../ROADMAP.md).

1. **Qualified constructors.** Every case is written with its type (`status::paid`, `option::some(x)`, `result::ok(sum)`), even where the expected type already determines it. This keeps one way to write each value and makes code readable out of context, at the cost of length. The alternative is bare cases where a type is expected (`return paid;`). `case` already names cases without their type (§ 8.16).
2. **Field order in record literals.** Fields are written in declaration order (§ 8.11). It is easy to relax later and impossible to tighten, which is why the strict rule comes first.
3. **Equality of heap values.** `==` only applies to strings among the heap types (§ 8.3). Structural equality for records, lists, options and results is convenient but hides a deep traversal; identity equality (`ref.eq`) exposes something the boundary does not preserve (§ 10.10). Neither is in the language.
4. **The cost of `list::freeze`.** `list<T>` is really immutable (§ 7.10), so a list built element by element is copied once by `list::freeze`. A compiler could skip the copy when the mutable list is not used after `freeze`, but that is an optimization, not a rule of the language. The real fix is in WasmGC: a way to build an immutable array from values computed at run time (§ 12.5).
5. **Text formatting.** `text::from_u32` in § 15.3 is the kind of function every project needs. It belongs to the standard library, which does not exist yet; until then, projects write their own.
6. **Flags operators.** Flags have `|`, `&`, `==` and a test per flag (`d.paper`). There is no complement (`!`) or difference: they are easy to add if programs need them.
7. **Tests.** How tests are declared and discovered by `weasel test`.
8. **Libraries.** How WaSL libraries are distributed: as source packages, or as components composed with `wac`.
9. **JSON.** A library written in WaSL, plus code generated from WIT records by a tool outside the compiler.
10. **Handles in data structures.** A handle cannot be stored in a record, a list, a tuple, a field or a global, and an `option` or a `result` that holds one is only a temporary (§ 7.12, E0220). This keeps ownership in locals, where releasing a handle is a local decision (§ 9.9). A pool of connections or a list of open files needs more: either an explicit release, or release functions generated per type, run when a value is overwritten or leaves its scope. WASI 0.2 HTTP returns nested handles (`option<result<result<incoming-response, error-code>>>`), so the question comes back with `wasi:http` in 0.4.
11. **Resources in foreign exports.** A world cannot export a foreign interface that declares resources (§ 13.12): the block would need a syntax to implement them. No target program needs it yet.
12. **WIT names without a WaSL spelling.** A name of a dependency with uppercase letters, a word starting with a digit, or a WaSL keyword cannot be named (§ 13.2). An escape, such as WIT's `%`, would make every name reachable.
13. **Which world provides a same-package import.** `weasel call` takes the first world that exports the interface (§ 14.2). A project with several candidates may want to choose; the choice belongs to composition, which is a tool's job, not the language's.

**Settled.** The error propagation operator `?`, an open question of v0.2, is specified in § 8.19 for 0.3. The `gc` option of the Canonical ABI will let WasmGC references cross component boundaries; the adapters of chapter 13 then disappear, and so do the copies of § 10.10. Nothing that is copied at the boundary can change (§ 7.11), and resources are passed by handle, never copied (§ 10.11), so no program can depend on receiving a private copy, and the copies can disappear without changing any behavior.
