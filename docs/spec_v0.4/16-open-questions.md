# 16. Open questions

These questions were met while writing the target programs and the specification. Each one has a default in the chapters above; this list says where the default is weakest. Features already planned, such as the standard library, are in [ROADMAP.md](../../ROADMAP.md).

1. **Qualified constructors.** Every case is written with its type (`status::paid`, `option::some(x)`, `result::ok(sum)`), even where the expected type already determines it. This keeps one way to write each value and makes code readable out of context, at the cost of length. The alternative is bare cases where a type is expected (`return paid;`). `case` already names cases without their type (§ 8.16).
2. **Field order in record literals.** Fields are written in declaration order (§ 8.11). It is easy to relax later and impossible to tighten, which is why the strict rule comes first.
3. **Equality of heap values.** `==` only applies to strings among the heap types (§ 8.3). Structural equality for records, lists, options and results is convenient but hides a deep traversal; identity equality (`ref.eq`) exposes something the boundary does not preserve (§ 10.10). Neither is in the language.
4. **The cost of `list::freeze`.** `list<T>` is really immutable (§ 7.10), so a list built element by element is copied once by `list::freeze`. A compiler could skip the copy when the mutable list is not used after `freeze`, but that is an optimization, not a rule of the language. The real fix is in WasmGC: a way to build an immutable array from values computed at run time (§ 12.5).
5. **Text formatting.** `text::from_u32` in § 15.3 is the kind of function every project needs. It belongs to the standard library, which does not exist yet; until then, projects write their own.
6. **Flags operators.** Flags have `|`, `&`, `==` and a test per flag (`d.paper`). There is no complement (`!`) or difference: they are easy to add if programs need them.
7. **Tests.** How tests are declared and discovered by `weasel test`.
8. **Libraries.** How WaSL libraries are distributed: as source packages, or as components composed with `wac`.
9. **JSON.** A library written in WaSL, plus code generated from WIT records by a tool outside the compiler.
10. **Handles in data structures.** A handle cannot be stored in a record, a list, a field or a global, and an `option`, a `result` or a tuple that holds one is only a temporary (§ 7.12, E0220). This keeps ownership in locals, where releasing a handle is a local decision (§ 9.9). A pool of connections or a list of open files needs more: either an explicit release, or release functions generated per type, run when a value is overwritten or leaves its scope. WASI 0.3 returns several handles in tuples, which 0.4 destructures (§ 9.4); a program that keeps handles in a data structure is still to come.
11. **Resources in foreign exports.** A world cannot export a foreign interface that declares resources (§ 13.12): the block would need a syntax to implement them. No target program needs it yet.
12. **WIT names without a WaSL spelling.** Since 0.4, uppercase letters are written in lowercase (§ 13.2). A name of a dependency with a word starting with a digit, or that is a WaSL keyword, still cannot be named. An escape, such as WIT's `%`, would make every name reachable.
13. **Which world provides a same-package import.** `weasel call` takes the first world that exports the interface (§ 14.2). A project with several candidates may want to choose; the choice belongs to composition, which is a tool's job, not the language's.
14. **A marker for waits.** A call to an async function is written like any call (§ 2.8): the Component Model has no `await`, and the color of each function is in its WIT. The cost is that the points where other tasks may run are not visible in the text. This is the only decision of 0.4 that cannot be changed later without breaking programs, so it is reviewed when the specification is frozen in 0.5, after the standard library has been written with it. What would reopen it: races on globals in real programs, or AI agents that misjudge where a function waits.
15. **Concurrency inside a task.** `async f(x)` will start a call without waiting and return a `subtask<T>`, the `canon lower async` of the Component Model, and `subtask::wait(t)` will wait for its result. A subtask that is not waited for by the end of its block will be cancelled, then waited for, like a handle released at the end of its block (§ 9.9), so that no task is ever left running without an owner. On a function of an imported interface this works with WASI 0.3; on a function of the package it needs the threads of the Component Model. Waiting for the first of several subtasks, for a timeout, goes through waitable sets and waits for a program that needs it.
16. **Several tasks in one instance.** The components of 0.4 run one async task at a time (§ 13.13). The stackful tasks and the threads of the Component Model, planned for a later release of WASI, let one instance interleave many tasks with the same body: only the adapters and the placement of the regions of linear memory change. Threads also lift E0419: a function that contains `task::return` can then be called by the package, on a thread of its own, and deliver its result to its caller (§ 8.21).
17. **Cancellation.** A task is not told that its caller cancelled it (§ 10.12). A built-in function such as `task::cancelled()` would let a long loop stop early; it waits for a program that needs it.
18. **Lending the end of a stream.** A stream end cannot be borrowed (§ 7.13): a function of the package that writes to a stream takes its writable end, and closes it or returns it. A `borrow` of an end, inside the component only, would be closer to how programs share a writer.
19. **Futures that are never written.** Releasing a `future_writer<T>` without a value traps (§ 10.7); the compiler does not see it, because that would need a flow analysis. Creating a future just before writing it keeps the risk small.

**Settled.** The error propagation operator `?`, an open question of v0.2, is specified in § 8.19 for 0.3. Async, planned since 0.1, is specified for 0.4 in § 2.8 and § 8.21, with streams and futures (§ 7.13). The `gc` option of the Canonical ABI will let WasmGC references cross component boundaries; the adapters of chapter 13 then disappear, and so do the copies of § 10.10. Nothing that is copied at the boundary can change (§ 7.11), and resources are passed by handle, never copied (§ 10.11), so no program can depend on receiving a private copy, and the copies can disappear without changing any behavior.
